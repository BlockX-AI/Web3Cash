The core insight
GrowStreams is a protocol for quality-verified work → streaming payment. Web3Cash is a protocol for action-verified engagement → direct payment. The verification pipeline, identity layer, anti-gaming system, and campaign infrastructure are identical. Only the quest type and payout model differ.

  • Wire Gitcoin Passport API at registration route
  • Add ?ref= param capture on landing → cookie → referral row on register
  • Identity Registry contract: same as GrowStreams — no changes
Week 2 — New Quest Workers
Build the 3 quest verification workers
GrowStreams has GitHub PR scoring and X content scoring. Web3Cash needs Twitter follow-check, Discord join-check, and deposit verification. These are BullMQ workers — simpler than LLM scoring.
  • TwitterFollowWorker: GET /2/users/:id/following → binary pass/fail
  • Delayed job at T+72h: re-check follow → VERIFIED or CANCELLED
  • DiscordJoinWorker: getChatMember(guildId, userId) → pass/fail
  • Discord leave detection: GUILD_MEMBER_REMOVE webhook → cancel payout
  • DepositWorker: Alchemy getAssetTransfers → verify tx to target address
  • Anti-fraud: velocity limits (5 quests/day/wallet via Redis INCR)
  • Anti-fraud: one Twitter per wallet (reuse GrowStreams unique constraint)
Week 3 — Payout + Referral Engine
Wire the money flow end-to-end
GrowStreams uses a pool-at-end payout. Web3Cash pays directly per-action after 72h hold. The referral bonus calculation runs on the same event — simple math, one DB query.
  • Gnosis Safe setup: 2-of-3 multisig, deposit test USDC, test batch send
  • Payout queue: at T+72h pass → INSERT payout row status=PENDING_RELEASE
  • Admin panel: view PENDING_RELEASE payouts → export CSV for Gnosis
  • Referral bonus: on payout confirmed → 10% to L1 referrer, 3% to L2
  • User balance dashboard: total earned + pending + referral earnings
  • Withdrawal request: user enters wallet → threshold check → queue
  • Airtable sync: project completions view (reuse GrowStreams campaign pattern)
Week 4 — Frontend + Launch
Build the 4 missing pages
GrowStreams is also building registration + dashboard + leaderboard in Sprint 2. Build these once with a config flag that switches the UX between GrowStreams mode (XP leaderboard) and Web3Cash mode (quest feed + balance).
  • Registration page: wallet connect → OAuth → sybil gate → track select
  • Quest feed page: active campaigns, reward amounts, start quest CTA
  • User dashboard: balance, pending, referral link, withdrawal form
  • Campaign rules page: project info, quest types, payout formula
  • Telegram bot: payout confirmed notification + new quest alerts
  • Mobile check: wallet connect on MetaMask mobile + WalletConnect QR

New User Flow — Web3Cash on GrowStreams Infrastructure

From landing page to USDC in wallet —
annotated with what's reused vs new.

01
User lands on web3cash.io — clicks Connect Wallet
GrowStreams: RainbowKit + wagmi wallet connect — reuse exactly
MetaMask or WalletConnect pops up. User signs a message (no gas). Wallet address captured. Session JWT created. This code is identical to GrowStreams registration — the wallet connect + signature verification layer is shared completely.
02
Sybil score checked via Gitcoin Passport API
Web3Cash NEW — GrowStreams uses LLM content check instead
On first login: POST to Gitcoin Passport Scorer API with wallet address → returns a 0–100 humanity score. Score ≥ 20 = quest access granted. Score below 20 = blocked with explanation. Stored in participants.sybil_score. This replaces the PR content similarity check from GrowStreams — same timing, different gate.
03
User connects Twitter via OAuth 2.0 PKCE → account linked to wallet
GrowStreams: X OAuth flow reused exactly — same code path
User clicks Connect Twitter → redirect to Twitter OAuth → callback receives access token → token stored encrypted in participants table (same column, same encryption as GrowStreams). Identity Registry contract called: wallet ↔ twitter_id binding written on Vara. One Twitter account per wallet enforced via UNIQUE constraint — same as GrowStreams.
04
Referral attribution — if ?ref= param present on landing
Web3Cash NEW — GrowStreams has no referral system
If user arrived via a referral link (?ref=W3C-XXXX), the code was stored in a cookie on landing. On registration: INSERT INTO referrals(referrer_wallet, referee_wallet). This is a single DB write. Referral dashboard shows the referrer their L1/L2 earnings in real time. This entire module is new — 2 DB rows and a query, nothing complex.
05
User sees quest feed — 3 active quests shown
Web3Cash NEW — replaces GrowStreams OSS issue browser
Quest feed shows: project name, what to do (Follow @ProjectX), reward in USDC, spots remaining. Data comes from the quests table (new). Click "Start Quest" → creates quest_completion row with status PENDING — same pattern as GrowStreams contributions table but for engagement quests, not code PRs.
06
TwitterFollowWorker verifies the follow — BullMQ job
Web3Cash NEW — replaces GrowStreams LLM PR scoring
User clicks Follow on Twitter. Returns to site. Clicks "I followed" → triggers BullMQ job: TwitterFollowWorker calls GET /2/users/:id/following with the stored access token. Is target account in the results? Yes → VERIFIED. No → FAILED. Takes ~500ms. Returns result to user immediately. This is the same job queue infrastructure as GrowStreams — just a different worker function.
07
72-hour delayed job scheduled — the unfollow hold
GrowStreams: BullMQ delayed job pattern — same queue infrastructure
bullmq.add('recheck-follow', {completionId}, {delay: 72*60*60*1000}) — this is the GrowStreams T+6h / T+24h re-evaluation pattern applied to the follow-check problem. The queue is the same Upstash Redis instance. The job fires at exactly T+72h and re-runs the GET /following check. Still following = payout released. Unfollowed = payout cancelled + wallet flagged.
08
Payout queued — admin approves in Gnosis Safe weekly
Web3Cash NEW — GrowStreams uses SQL-to-manual USDC batch on Day 21
At T+72h pass, INSERT payout row: status=PENDING_RELEASE, amount_usdc=17.00, wallet=user. Admin panel shows PENDING_RELEASE payouts. Admin clicks Export → CSV with wallet:amount → imports into Gnosis Safe batch. 2-of-3 multisig signers approve. USDC flows on-chain. UPDATE payout status=CONFIRMED + tx_hash stored. This is the same admin-executed payout model GrowStreams uses on Day 21 — just triggered weekly rather than once.
09
Referral bonus credited to referrer — L1 and L2
Web3Cash NEW — GrowStreams has no referral layer
On payout CONFIRMED: query referrals table for this referee's referrer. L1 referrer gets 10% of gross reward added to pending_balance. L2 referrer (referrer's referrer) gets 3%. These are queued to the next Gnosis Safe batch. Simple arithmetic. No smart contract needed. Max 2 levels — enforced by only walking 2 hops up the referral chain in the query.
10
User sees updated balance + Telegram notification
GrowStreams: Telegram bot pattern reused — build once for both
Supabase Realtime updates the user's balance in the dashboard. Telegram bot (built in GrowStreams Sprint 3) sends: "You just earned $17 USDC — tx hash: 0x...". The Telegram bot is built once and serves both GrowStreams participants and Web3Cash users. Different message templates, same bot infrastructure. User can now share their referral link from the dashboard.

User Flow Level Bugs & Concerns

GrowStreams plan vs Web3Cash reality —
every gap that breaks the user journey.

These are the exact points where GrowStreams's documented flows, if applied naively to Web3Cash, would create broken experiences. Each one is a design mismatch that needs a specific fix in the extension.

01
CRITICAL · Flow Breaking
GrowStreams scores quality (0–100). Web3Cash verifies action (pass/fail). The LLM rubric is wrong for Web3Cash quest types.
GrowStreams sends PR diffs to GPT-4o for a quality score. Web3Cash needs a binary API check: does this wallet follow that Twitter account? Using the LLM rubric for a follow-check is like using a PhD committee to approve a checkout. The GrowStreams agent code must NOT be copy-pasted into Web3Cash quest workers. Replace with: Twitter API GET /following → boolean. Discord getChatMember → boolean. Alchemy getAssetTransfers → boolean. Zero LLM calls needed for these quest types.
BLOCKER
02
CRITICAL · Flow Breaking
GrowStreams pays from a pool at Day 21. Web3Cash pays per action after 72h. The payout model is fundamentally different — using GrowStreams payout logic gives wrong amounts to wrong people.
GrowStreams: your USDC = (your XP / total XP) × $500. This is a proportional distribution — early quitters get less, late joiners get less. Web3Cash: your USDC = fixed reward per quest × number of verified quests. $17 per Twitter follow. $25 per Discord join. These are independent per-action payouts, not a shared pool. If you apply GrowStreams's Day 21 SQL query to Web3Cash, you'll underpay high performers and overpay low performers. The payouts table and Gnosis Safe batch logic must be purpose-built for Web3Cash.
BLOCKER
03
CRITICAL · Trust Breaking
GrowStreams has no 72-hour hold. Web3Cash without the hold loses $500 to follow-farmers on Day 1.
GrowStreams accumulates XP over 21 days — gaming it requires sustained effort. Web3Cash quests can be completed and re-submitted immediately without a hold. A follow-farmer can: follow → claim reward → unfollow → follow again → claim again. The 72-hour BullMQ delayed job is not optional — it is the anti-fraud primitive that makes the economics viable. GrowStreams's T+6h/T+24h re-evaluation jobs are the right pattern — just extend to T+72h. This must be in the first working code, not a later sprint.
BLOCKER
04
HIGH · UX Breaking
GrowStreams has no referral system. Web3Cash without referral tracking from registration means referral codes stored after sign-up are useless — attribution is broken.
GrowStreams captures wallet + OAuth and calls it done. Web3Cash must capture the ?ref= URL parameter BEFORE the user connects their wallet — it needs to survive the OAuth redirect. Store ref code in a cookie on landing. On registration INSERT INTO referrals. If the cookie is captured AFTER OAuth completes, the HTTP redirect from Twitter OAuth will clear URL params and the referral attribution is permanently lost. The fix: set the cookie on the landing page load itself, not on the registration form submit.
MUST FIX
05
HIGH · Trust Breaking
GrowStreams shows XP as the trust signal. Web3Cash needs USDC balance as the trust signal. The leaderboard mechanic is wrong for Web3Cash — users care about dollars, not points.
GrowStreams's leaderboard (rank #1, 8,400 XP) creates competitive FOMO that drives participation. This works when XP → USDC conversion is transparent. Web3Cash should show: "You have $34.00 earned, $17.00 pending release." Dollar amounts are more compelling than XP for a cashback product. Do not port the GrowStreams leaderboard UI into Web3Cash. Build a balance-first dashboard instead. The referral earnings breakdown (you earned $6.80 from 4 people you referred) is the engagement mechanic for Web3Cash, not the rank position.
MUST FIX
06
HIGH · Completeness Breaking
GrowStreams's GitHub App is an OSS contribution tool. Web3Cash's GitHub quest would be "star this repo" or "fork this repo" — totally different actions requiring different API calls.
If you add GitHub as a quest type to Web3Cash (future), do not reuse the GrowStreams GitHub agent code. GrowStreams: fetch PR diff → LLM score → XP. Web3Cash (GitHub quest): GET /repos/{owner}/{repo}/stargazers → check if user's GitHub handle in list. Completely different API call, no LLM, binary result. The HMAC webhook handler and GitHub App setup can be reused, but the agent logic must be a new worker. Don't let a developer assume the existing GitHub agent handles Web3Cash GitHub quests.
MUST FIX
07
MEDIUM · Flow Gap
GrowStreams's score ≥ 70 threshold has no user appeal path. Web3Cash's binary pass/fail has an even harsher UX — user follows, verification fails silently, they don't know why.
GrowStreams posts a GitHub comment explaining why a PR scored 58/100. This is good UX — developer knows exactly what to fix. Web3Cash's TwitterFollowWorker returns FAILED with no public comment (no X agent reply for a failed follow). The user sees "verification failed" with no explanation. Add: show the user the exact follow check result. If GET /following returns no match, show: "We couldn't verify you follow @ProjectX. Make sure your Twitter account is connected and the follow is public. Private accounts cannot be verified." Silent failures in Web3 destroy trust faster than anything else.
FIX IN SPRINT 2
08
MEDIUM · Fraud Gap
GrowStreams caps at 3 OSS + 10 content posts per wallet. Web3Cash needs per-quest limits, not per-track limits — a user should only be able to complete each specific quest once.
GrowStreams: max 3 PRs per wallet across the entire campaign. Web3Cash: max 1 completion per quest per wallet (enforced by UNIQUE(quest_id, wallet) constraint), but across different quests a user can complete as many as exist. These are different limit semantics. GrowStreams's velocity limit code would wrongly block a user from completing their 4th quest when they should be allowed to (it's a different project). Reuse the UNIQUE constraint pattern, not the count limit logic.
FIX IN SPRINT 1
09
WEB3CASH SPECIFIC · New Risk
GrowStreams has no concept of "project escrow verification." Web3Cash must prove the $500 USDC exists before users can start quests — otherwise it's a rug-pull waiting to happen.
GrowStreams shows the $500 pool on the campaign page with a Vara wallet link. Web3Cash must do the same: show the Gnosis Safe wallet address with a live USDC balance link on the quest page. If a user completes a quest and then discovers there's no money in the escrow, the damage to trust is permanent. The campaign page should load the actual USDC balance from the Gnosis Safe on every page load. If the balance drops to zero before all quests are filled, quests should automatically mark as "Budget depleted" and stop accepting new completions. This is not in GrowStreams's design — it's a Web3Cash-specific trust primitive.
WEB3CASH ONLY
10
WEB3CASH SPECIFIC · New Risk
GrowStreams's XP never expires. Web3Cash's pending payouts must expire if the project cancels the campaign — users need to know their 72h hold could result in $0 if escrow runs dry.
In GrowStreams, XP accumulates until Day 21 regardless of what happens to the campaign pool. In Web3Cash, a project could deposit $500, get 30 completions totaling $510, and not have enough for all of them. The payout queue must enforce: before marking a completion as PENDING_RELEASE, check that quest.remaining_budget ≥ reward_usdc. If not, cancel the completion with a clear "Campaign budget exhausted — your completion will not be paid" notification. First come, first served. This ordering must be documented publicly on the campaign page before any user starts a quest. Otherwise it's a legal liability.
WEB3CASH ONLY

Summary Verdict

The honest numbers on time saved,
risk reduced, and what's still genuinely new.

Dev time saved
~9 days
GrowStreams's infra handles identity, anti-gaming, LLM pipeline, Railway deployment, Supabase setup, and BullMQ queue — all the hard parts. Web3Cash focuses 4 weeks on quest logic and payout flow instead of rebuilding foundations.
What's genuinely new
5 items
1. TwitterFollowWorker (API check, not LLM). 2. 72h delayed job. 3. Referral engine (L1/L2). 4. Per-action direct payout model. 5. Gnosis Safe budget tracking per quest. Everything else is GrowStreams with different config.
Biggest risk
3
Three things from GrowStreams must NOT be reused as-is: (1) LLM rubric for quest verification, (2) Day 21 proportional payout SQL, (3) per-track velocity limits. These three copy-paste mistakes would break the product in ways that are hard to debug and lose user trust.
Bottom lineWeb3Cash is GrowStreams with different quest types, a per-action payout model instead of a pool, and a referral engine. Build it as a new module in the same codebase — not a separate repo. Share Railway, Supabase, Redis, and the Identity Registry contract. Fork only what needs to differ.
