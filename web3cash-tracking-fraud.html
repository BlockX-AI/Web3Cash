The 5 Performance Marketing Metrics

CPC, CPA, CPI, CPS, CPL — explained like you're explaining it to a friend.

These are the five ways advertisers pay for marketing. Instead of paying upfront for ads that might work, performance marketing means you only pay when something specific happens. Think of it like: "I'll pay you only after the pizza is delivered, not when you take the order."

CPC
Cost Per Click
You pay when someone clicks your ad
The oldest model. A user sees your banner or ad, clicks it — you pay. Doesn't matter if they buy anything, sign up, or even stay on your page. Just the click.
Typical rate: $0.10 – $2.00 per click
Web3Cash equivalent: Site visit quest — $0.10
Main fraud: Click farms — bots click your ad thousands of times, draining your budget with zero real users.
CPA
Cost Per Action
You pay when someone takes a specific action
You define the action — could be anything: connect a wallet, make a deposit, complete a trade, stake tokens. You only pay when that exact thing happens and is verified.
Typical rate: $5 – $50 per action
Web3Cash equivalent: Wallet connect — $5, Deposit — $15
Main fraud: Simulated actions — bots that trigger the action event without actually doing the thing (fake wallet connects, simulated deposits).
CPI
Cost Per Install
You pay when someone installs your app or dApp
Most common in mobile apps and now Web3 dApps. The user must actually open and use the dApp, not just visit the page. Modern CPI tracks first session events — not just the install itself.
Typical rate: $2 – $20 per install
Web3Cash equivalent: dApp install quest — $10
Main fraud: Install farms — emulators running thousands of virtual phones or browsers, simulating installs at scale.
CPS
Cost Per Sale
You pay only when a real sale or revenue event happens
The hardest to fake — money actually has to move. In Web3 this means a real deposit above a minimum threshold, a real trade, or a real token purchase. The blockchain makes this trivially verifiable.
Typical rate: 5–15% of transaction value
Web3Cash equivalent: First deposit above $100 — $15
Main fraud: Wash trading — bots trade with themselves to fake volume. Detectable by checking if the same wallet is both buyer and seller.
CPL
Cost Per Lead
You pay when someone signs up or registers
A lead is a potential customer who has shown interest by registering. In Web3 this is a wallet that connects and creates a profile — indicating real intent to use the product.
Typical rate: $1 – $10 per lead
Web3Cash equivalent: Twitter follow + wallet link — $1
Main fraud: Bot signups — scripts creating thousands of fake email addresses or wallet addresses to collect lead payouts.

Simple analogy — remember this forever
CPC is paying someone to look at your restaurant menu. CPL is paying when they make a reservation. CPI is paying when they walk in the door. CPA is paying when they order food. CPS is paying when they pay the bill. Only the last two prove they were actually hungry.
How Traditional Tracking Works — Offer18 / HasOffers Style

How platforms like Offer18 track every click, install, and conversion.

Offer18, HasOffers, Adjust, AppsFlyer — these are all affiliate tracking platforms. They solve the same problem Web3Cash solves, but for Web2 apps. Understanding how they work is critical, because Web3Cash needs to do everything they do plus verify on-chain truth.

The Core Problem
How do you know which affiliate sent which user?
Imagine you run 10 different affiliates (influencers, apps, websites) all sending you users. When a user converts, you need to know which affiliate to pay. Without tracking, you're flying blind. You'd have to trust every affiliate's self-reported numbers — which is a disaster.
The Solution
Unique Click IDs + Postback URLs
Every affiliate gets a unique tracking link. Every click generates a unique Click ID. When a conversion happens, the server sends that Click ID back via a postback URL — a server-to-server notification. No cookies needed. Works even if the user clears their browser.

The 6-step tracking chain — how Offer18 style tracking works

01
Affiliate gets a unique tracking link
Each affiliate (influencer, app, website) is given a tracking URL with their unique affiliate ID embedded. When they share this link, every click is tagged.
https://track.web3cash.io/click?offer_id=42&aff_id=101&aff_sub=tg_alpha_group
02
User clicks the link — a Click ID is generated instantly
The tracking server creates a unique Click ID for this specific click — timestamp, affiliate, device fingerprint, IP. Stores it in a database. Redirects the user to the actual destination.
Click ID: clk_9f8a2b1c4e7d → stored with IP, device, timestamp, affiliate 101
03
Click ID travels with the user — passed to the dApp
The user arrives at the dApp with the Click ID in the URL. The dApp stores this Click ID — in a cookie, localStorage, or the URL for the session. This is how the conversion is later tied back to the original click.
https://dapp.com/register?clk=clk_9f8a2b1c4e7d&ref=web3cash
04
User completes the action — dApp fires a postback
When the user converts (deposits, trades, installs), the dApp's server sends a server-to-server postback to Web3Cash's tracking endpoint — passing the Click ID and conversion details. This is not a browser pixel — it's a server call. Cannot be blocked by ad blockers.
GET https://track.web3cash.io/postback?click_id=clk_9f8a2b1c4e7d&event=deposit&amount=150
05
Web3Cash validates the postback + cross-checks on-chain
Unlike Offer18, Web3Cash doesn't just trust the postback. We verify it on-chain — does the wallet address that made this deposit actually have a deposit transaction matching the amount and timestamp? This is the unfakeable layer Web3 gives us.
SELECT tx FROM alchemy WHERE wallet=0x... AND amount≥150 AND block_time BETWEEN t-30min AND t
06
Attribution confirmed — payout queued
Postback confirmed + on-chain verified = conversion is real. Web3Cash records the conversion against affiliate 101, queues the USDC payout to the user, and records the platform margin. All stored with the tx hash as permanent proof.
Conversion confirmed: clk_9f8a2b1c4e7d → aff_101 → user wallet 0x... → payout $15 USDC queued

The Web3 Verification Advantage

Why blockchain makes Web3Cash's tracking unfakeable where Offer18 cannot be.

The core insight
Offer18 and HasOffers must trust what the dApp's server reports. A corrupt dApp can fire fake postbacks for fake users. Web3Cash doesn't have this problem — the blockchain is a public, immutable record that nobody can fake. We verify every conversion independently, without trusting anyone.
Web2 Tracking Problem
Trust-based — easy to manipulate
Offer18 relies on: browser cookies (deleted after 7 days, blocked by Safari ITP), device fingerprinting (spoofable with VPNs and emulators), and server postbacks (can be faked by a dishonest partner). If the affiliate and the advertiser collude, they can fake thousands of conversions. Offer18 has no way to independently verify.
Web3Cash Advantage
Truth-based — the chain never lies
Every on-chain action is publicly verifiable by anyone, forever. A deposit transaction has a tx hash. That tx hash has a timestamp, wallet address, amount, and contract address. Nobody can fake a tx hash on a real blockchain. We don't need to trust the dApp's server report — we check the chain directly. This is why Web3 CPS/CPA fraud is fundamentally harder than Web2 CPA fraud.

Sybil Attacks — Explained Simply

What is a Sybil attack and why is it the biggest threat to Web3Cash?

Simple analogy — Sybil attack in one sentence
A Sybil attack is one person creating thousands of fake identities to claim rewards meant for thousands of different people. Named after a 1973 book about a woman with 16 personalities — in Web3, one person has 16,000 wallets.

In Web3, creating a new wallet takes 3 seconds and costs nothing. A single person with a script can create 10,000 wallets overnight. If Web3Cash doesn't detect this, that person could drain an entire $20,000 campaign budget in one night — the project gets 10,000 "users" who are all the same bot, and real users get nothing.

How a real Sybil attack works — step by step

1
Attacker generates 10,000 wallets with a script
Using tools like ethers.js or web3.py, one script creates 10,000 new Ethereum wallets in minutes. Each wallet gets a tiny amount of ETH for gas from a "funder wallet" — often bought with a prepaid card or Monero to hide the source.
for i in range(10000): wallet = create_wallet() send_gas(wallet, 0.001 ETH)
2
Bot visits Web3Cash and connects each wallet
Headless browser automation (Playwright or Puppeteer) opens Web3Cash, connects each wallet, signs the auth message programmatically. 10,000 accounts created in hours. Each has a unique wallet address — looks like 10,000 different users.
3
Bot completes quests for each wallet
For simple quests (site visit, Twitter follow with bought accounts), the bot can complete them for all 10,000 wallets. For on-chain quests, it makes tiny transactions to simulate activity. Each wallet claims its $10 USDC reward.
4
$100,000 drained — project gets zero real users
If Web3Cash paid out all 10,000 completions at $10 each, the attacker made $100,000 minus the small gas costs (~$500). The project paid for 10,000 "users" who are all the same person. Campaign budget completely drained in hours.

The 7-signal Sybil detection engine

01
Wallet Age
How old is the wallet? Fresh wallets created in the last 7 days are very suspicious. Real users have wallets months or years old.
Less than 7 days = 0 pts
Over 6 months = 10 pts
02
Transaction Count
How many transactions has this wallet made on-chain? Bots have 0–5 transactions. Real users have 20, 50, 100+ transactions over time.
Under 5 tx = 0 pts
Over 50 tx = 15 pts
03
Gas Spend History
Total ETH spent on gas over the wallet's lifetime. Bots spend the minimum. Real active users spend gas regularly on real transactions.
Under $1 gas total = 0 pts
Over $20 gas = 15 pts
04
DeFi Interactions
Has the wallet ever used Uniswap, Aave, Compound, or Curve? Real DeFi users interact with multiple protocols. Bots don't waste gas on real DeFi unless it's part of the attack.
Zero DeFi = 0 pts
3+ protocols = 20 pts
05
Token Diversity
How many different ERC-20 tokens has this wallet ever held? Bots typically only have ETH or USDT. Real users have diverse token portfolios from actual use.
Only ETH = 0 pts
5+ tokens = 10 pts
06
Source of Funds
Where did this wallet's first ETH come from? All bot wallets funded from the same source wallet is the clearest Sybil signal. We cluster wallets by funder address.
Funded from known bot wallet = -50 pts
Exchange withdrawal = +15 pts
07
Timing Patterns
Did 50 wallets all complete the same quest within 30 seconds of each other? That's a bot. Real users complete quests spread out over hours and days. Velocity clustering is a key fraud signal.
50 wallets same minute = flag all
Spread over 24+ hours = clean
08
Social Proof Score
Is a Twitter or Discord account linked? What's the account age, follower count, post history? Bots rarely have aged social accounts. Real users have verifiable online history.
No social linked = 0 pts
Verified Twitter 1yr+ = 15 pts

Fraud Types and Countermeasures

Every type of fraud you will face — and exactly how to stop each one.

Click Fraud
Bot clicks that drain CPC budgets
Automated scripts or hired humans click tracking links thousands of times to inflate click counts. The advertiser pays per click but gets zero users. Common on Google Ads, rare in Web3Cash since we don't pay on click alone.
Fix: Web3Cash minimum action is a wallet signature — bots cannot sign with a private key they don't have. CPC alone is never offered as a quest type.
Install Farming
Emulators faking app installs
Bot farms run thousands of virtual Android devices (emulators) that install dApps, open them once, and collect the CPI payout. The dApp's install event fires, looks real to a naive tracker.
Fix: Require wallet connect + on-chain interaction within 10 minutes of install. Emulators don't have real private keys or ETH. Also: check if install device fingerprint overlaps with other fraud claims.
Fake Deposits
Tiny deposits to trigger CPS
Attacker deposits $0.01 (or the exact minimum) to trigger a "first deposit" payout of $15. They withdraw immediately. Net: paid $0.01 gas + $0.01 deposit, received $15 reward. Classic CVS fraud.
Fix: Set minimum deposit thresholds that make sense economically (deposit must be at least 2x the quest reward). Also require deposit to remain in the dApp for 48 hours before payout.
Wash Trading
Trading with yourself to fake volume
For CPS quests tied to trading volume, attacker creates two wallets and trades between them. Wallet A sells 1 ETH to Wallet B, which sells it back. Volume appears real on the DEX, but it's all one person.
Fix: Check if counterparty in the trade is a known wallet of the same user. Flag if both sides of a trade funded from the same source address. Require trades with externally funded counterparties.
Referral Fraud
Self-referral with Sybil wallets
Attacker creates Wallet A and Wallet B. A refers B. B completes quests. A earns 10% of B's rewards forever — but A and B are the same person. At scale with 1000 wallet pairs, this is very profitable.
Fix: Flag referral pairs where referrer and referee wallets were funded from the same source. Require referees to have a Sybil score above 50 before referral reward is paid. Hold referral payouts for 72 hours for review.
Social Farming
Bought Twitter/Discord accounts
Attacker buys aged Twitter accounts in bulk (sold on black markets for $5–$50 each). Uses these to "follow" projects for CPL quests. Each account looks legitimate — old creation date, some followers, some tweets.
Fix: Check Twitter account engagement rate (followers/tweets ratio), recent activity patterns, and whether the account follows a suspicious number of crypto projects in a short window. Require account to be followed for 72 hours before payout.

Bot-Based Automated Verification

Building verification bots on GitHub, X, Discord, and Telegram.

For off-chain quests (social follows, GitHub stars, Discord roles), Web3Cash uses dedicated verification bots on each platform. These bots do not trust what the user claims — they independently check the platform's API in real time. Here is exactly how to build each one.

GitHub verification checks: did the user actually star a repo, fork it, or open an issue? A GitHub App (not a personal token) is the right approach — it scales to millions of checks without rate limits being an issue, and it can receive webhook events in real time rather than polling.

Install once — verify forever

  • Set webhook URL to your verification service endpoint
  • Subscribe to events: star, fork, watch, issues
  • Install the app on any repo that has an active quest campaign

Verification Logic
What the bot checks

  • Check account activity: at least 5 public contributions in last 90 days (catches bought accounts)
  • Webhook real-time: star event fires immediately — match to pending quest claims within 5 minute window
  • Store GitHub username → wallet address mapping to prevent one GitHub account claiming multiple wallets

  • Cache stargazer lists in Redis with 5-minute TTL to reduce API calls

    Automated Pipeline for Scale

    How to handle 100,000 users without breaking — queue architecture and automated flows.

    When Web3Cash has 100,000 users completing quests simultaneously, you cannot process verifications synchronously. Every verification is an async job in a queue. The user submits, gets "pending" immediately, and the result arrives within 60 seconds. Here is the complete pipeline architecture.

    Every completion claim becomes a BullMQ job. Multiple workers process jobs in parallel. Workers fan out to the appropriate verification module — on-chain indexer for blockchain actions, platform bots for social actions. Results flow back to a central result handler that updates the database and queues payouts.

    Verification jobs can fail for many reasons — blockchain indexer slow, Twitter API rate limit, Discord API timeout. The retry strategy uses exponential backoff to handle temporary failures gracefully without hammering external APIs. After 3 failed attempts, the job goes to a dead-letter queue for manual inspection.

    The Complete Anti-Fraud Checklist

    Everything to ship before your first real campaign goes live.

    Before Launch — Must Have
    □
    Sybil scoring engine live — wallet age, tx count, gas spend, DeFi interactions all scored before first quest access
    □
    Minimum score gate on all quests — even free quests require Sybil score above 20. Zero-score wallets cannot claim anything
    □
    Velocity limits in Redis — max 5 quest claims per wallet per hour. Rate limit stored as Redis INCR with 1 hour TTL
    □
    30-minute payout hold — no payout released immediately. All verified completions held 30 minutes for fraud check sweep
    □
    Funder wallet clustering — reject completions where 3 or more wallets claiming the same quest were funded from identical source address
    □
    On-chain idempotency — tx hash stored in verification_logs. Same tx hash cannot be used to verify two different completions ever
    □
    Payout pause button — admin can halt all payouts instantly via smart contract circuit breaker. Requires multisig. Test this before launch
    □
    KYC gate at $500 — any wallet attempting to withdraw more than $500 USDC in a rolling 30-day window must complete KYC
